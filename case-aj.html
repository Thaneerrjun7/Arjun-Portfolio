Case study · AJ

The GPU fell asleep while I was talking

AJ is a voice assistant that runs on my own Windows laptop, on a 6 GB GPU. A voice assistant lives or dies on how long you wait after you stop talking, so I measured every stage. This page is about three problems those measurements showed me, and what fixed each one.

Personal projectAI-assisted2026, in progressPython, llama.cpp, Qwen3-4B, SQLite

Problem 1: the first reply was slow for no obvious reason

With a cached prompt, the model reaches its first sentence in a median of 137 ms. But on a real turn, prompt processing alone was taking 250 to 330 ms. The cause was the laptop, not the model: while I am talking the GPU has nothing to do, so it drops to a lower clock speed to save power, and the first request after that pays for the wake-up.

The fix is small. While the microphone hears me speaking, AJ sends a one-token request to the model server every 0.4 seconds, on a second inference slot so the conversation's own slot is left alone. The GPU never gets the chance to slow down, and prompt processing drops to about 30 ms. It is a fix at the level of the hardware's power behaviour, not a llama.cpp setting.

Problem 2: the model server wanted memory the laptop did not have

The laptop has 16 GB of RAM, and other apps usually hold 78 to 87% of it. The llama.cpp server was taking 2.8 GB of that on top of the graphics memory the model already uses.

  • Starting the server with --load-mode none brought its RAM down to 0.75 GB.
  • --cache-ram 0 switches off a prompt cache that could otherwise grow to 8 GB.
  • On the GPU, the main model takes about 3.1 GB of the 6 GB, which leaves room for the on-demand reasoning model.

Problem 3: the memory made things up

AJ remembers facts about me between sessions. A small extraction step reads the conversation after I have gone quiet and pulls out anything worth keeping. In testing, with a loose prompt, that step invented a fact in 14 of 14 chats that contained none.

So a fact is now saved only if it quotes my own words, and that is checked in code before anything is stored, not left to the prompt. The extractor's output is also held to a JSON grammar: without the grammar it produced valid JSON only about 10% of the time, and with it, it recalled 78% of the facts in the test conversations.

What I did not measure: I do not have an after-number for the invented facts yet, so I do not quote one.

A decision: keep everything, send little

SivaSafe, the assistant before this one, deleted stored facts to stay under its memory limit, and I watched it forget things I had told it. AJ keeps every fact in SQLite and never deletes one. What is limited is what each prompt receives: about 600 tokens of core facts, kept stable so the server's prompt cache still works, plus up to 5 full-text search matches for the current turn. It is keyword search, not vector search.

Limits of these numbers

  • Everything was measured on one laptop: an RTX 4050 Laptop GPU (6 GB), a Ryzen 7 7840HS and 16 GB of RAM, under Windows 11.
  • The 0.83 to 1.37 s from the end of my sentence to the first sound is a benchmark figure. In live use with the current persona it is about 1.1 to 1.8 s.
  • Tool-call accuracy is 55 of 60 runs. At that sample size the margin is about 7 points either way.

How it was built: with AI-assisted development. I designed the system, chose the models from benchmark data and blind listening tests, and directed and tested every change. An AI coding assistant wrote much of the code under my direction.
