The model made up a number

KIRA+ is an AI financial health platform for Buy Now, Pay Later and consumer credit, built by a distributed team of five for the MAIC Nexus Challenge 2026. Kira means "to calculate" in Malay. My role is AI/ML developer.

Team of 5AI/ML developer2026, in progressPython, FastAPI, scikit-learn, SQLite

The rule we built around

Rules decide. The model predicts. The language model explains.

The scoring engine is deterministic and auditable: a 0-100 score across six weighted factors, plus a six-rule early-warning engine where each rule names the exact figure that triggered it. A RandomForest predicts financial stress. The language model's only job is to explain, in plain words, figures the engine has already computed. It never computes and it never advises.

What went wrong

In my own testing, the language model quoted a ringgit amount that the engine had never computed. It read well and it was wrong. In an app about people's money, one invented figure is enough to lose their trust.

What I built

engine computes the figures
        |
language model writes 3 to 5 sentences about them
        |
output guard: is every number in the reply one the engine produced?
               is there any banned advice phrase?
        |                              |
      pass: show the reply           fail: show the deterministic template instead
  • An output guard that rejects any reply quoting a figure the engine did not compute, or giving financial advice. A rejected reply falls back to a deterministic explanation template, so the user always sees something true.
  • A provider client that speaks an OpenAI-compatible chat completions API (Groq by default, switchable by configuration), with a 4-second timeout and the same template fallback, so a slow model never blocks the page.
  • The system prompt, with absolute rules: never compute, never advise, keep to 3 to 5 sentences.

The model behind the prediction

0.923ROC-AUC, RandomForest on held-out data
0.921ROC-AUC in 5-fold cross-validation
0.844ROC-AUC, logistic-regression baseline

Trained on 12,000 synthetic profiles, and compared against a logistic-regression baseline so the score has something to stand next to.

Two defects the tests missed

I worked test-first: 56 unit and integration tests for my services. Then I ran the whole app in a browser and walked the demo path, and found two defects the suites had not caught:

  • Starting the server plainly never created the SQLite schema, so the first "Save profile" returned a 500 error. The schema is now created on startup.
  • The explanation code only read an older payload shape than the dashboard was sending, so a swallowed error showed "explanation unavailable" on every load.

The test fixtures had hidden both. I fixed them and added regression tests.

The rest of the stack

I also worked across the rest of the stack with our full-stack developer: together we built the Next.js front end, the FastAPI back end and its APIs, the database schema, the Docker image and the GitHub Actions CI/CD pipeline, and I provisioned the server it deploys to.
